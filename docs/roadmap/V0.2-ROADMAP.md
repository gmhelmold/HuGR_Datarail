# v0.2 Roadmap — Multi-Node, Key Management, Production Hardening

**Target:** 2026-Q4  
**Scope:** Multi-node replication, real key management, QUIC production, operational tooling  
**Philosophy:** Single-node honest scope → Multi-node honest scope. Every claim testable, every boundary documented.

---

## 1. Key Management (Real, Not Inline)

**Problem:** `rail.toml` carries inline demo seeds. Production needs rotation, HSM/KMS integration, audit trail.

| Task | Spec | Acceptance |
|---|---|---|
| Key provider trait | `KeyProvider` trait with `get_seed(key_id) -> Result<[u8;32]>` | `datarail-spec` validates provider config |
| age/SSH agent provider | `age` CLI + SSH agent socket | `datarail run --source-key-age=...` works |
| AWS KMS / GCP KMS / Vault providers | Optional features `aws-kms`, `gcp-kms`, `vault` | Integration tests against mock/localstack |
| Key rotation CLI | `datarail key rotate <key_id> --provider=...` | Rotation updates watermark, old key archived |
| Audit log | Structured JSONL to stdout/file | Key access logged with timestamp, caller, key_id |

**Blocking:** None. Can start in parallel.

---

## 2. Multi-Node Replication (Wire the Tier)

**Problem:** Replication tier exists as library code (`datarail-replication`, `datarail-netblob`, `datarail-keyrouter`, `datarail-replicated-topic`) but not wired into CLI.

| Task | Spec | Acceptance |
|---|---|---|
| CLI: `datarail replicate` | `datarail replicate --topic <topic> --peers <addr> --quorum N` | Multi-node produce/fetch survives m-node loss |
| `netblob` server binary | `datarail-netblob-server --addr --blob-store-dir` | Serves `BlobStore` over TCP, TLS optional |
| KeyRouter integration | Consistent hashing, 0-reshuffle on peer change | Rebalance verified under churn |
| TieredLog offload | Hot local, cold to `netblob` + `ErasureStore` | Cold read reconstructs from m shards |
| Cross-node offset sync | OffsetCommit/Fetch replicated via Raft/etcd | Consumer group survives broker failover |

**Blocking:** Key management (peer auth needs keys). Can prep infra in parallel.

---

## 3. QUIC Production Hardening

**Problem:** QUIC substrate is dev-cert only, client accepts any server cert.

| Task | Spec | Acceptance |
|---|---|---|
| Server cert via key provider | `QuicServerConfig` pulls cert/key from `KeyProvider` | No inline certs in config |
| Client cert verification | `rustls::ServerCertVerifier` with pinned CA / SPIFFE | Wrong cert → handshake fail |
| ALPN + 0-RTT config | Configurable via `rail.toml` | 0-RTT replay protection documented |
| Connection migration | Client IP change → new path validation | Migration test passes |

**Blocking:** Key management (cert source). Can design API in parallel.

## Risk Register

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Key management scope creep | High | High | Freeze M1 scope to trait + 2 providers; defer Vault/AWS to v0.3 |
| Multi-node consensus complexity | Medium | High | Start with single-leader etcd; Raft later |
| QUIC cert rotation during connection | Low | High | Document 0-RTT replay risk; disable by default |
| Benchmark environment variance | Medium | Medium | Lock CI runner specs; document hardware |
